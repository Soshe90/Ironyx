# Setup — a working checkout

How to get from `git clone` to a running, testable, releasable Ironyx.
(This file used to describe turning a source overlay into a project. The
`android/`, `ios/` and `web/` folders are now committed, so that is over.)

Last verified end to end on Windows 11 with **Flutter 3.47.5 / Dart 3.13.4
(stable)** on 2026-09-20: `flutter analyze --fatal-infos --fatal-warnings`
clean; `dart format` clean on `lib/` and `test/`; `flutter test` 423 passed, 1 skipped, 0 failed.
`pubspec.yaml` declares `sdk: '>=3.6.0 <4.0.0'`.

## 1. Prerequisites

- Flutter stable on your `PATH` (`flutter doctor -v` clean for the platforms
  you build).
- Android: a JDK 17 and the Android SDK. Gradle installs the NDK, build
  tools and platform it needs on the first build.
- iOS needs a Mac. **Nothing in `ios/` has ever been built or run on one** —
  see `PLAN.md` Phase 4 and the iOS notes at the end.

## 2. Get dependencies and generate code

```bash
flutter pub get
dart run build_runner build
```

`build_runner` is **required before the first compile.** `*.g.dart` and
`*.freezed.dart` are gitignored, so providers such as
`themeModeControllerProvider` do not exist until you generate them; expect a
wall of "undefined name" errors if you skip it. (The installed
`build_runner` no longer accepts `--delete-conflicting-outputs`; conflict
deletion is the default.) Localizations are generated by `flutter pub get`
from `lib/l10n/*.arb` (`generate: true`); `lib/l10n/untranslated.json` lists
any key missing from a locale.

## 3. Verify

```bash
dart format --output=none --set-exit-if-changed .
flutter analyze --fatal-infos --fatal-warnings
flutter test
dart run tool/check_asset_licenses.dart      # what CI runs before building
```

The licence check passes on Windows as well as Linux (fixed 2026-09-20: it
used to compare `\`-separated paths from the filesystem with the seed's
`/` paths and report every image as unreferenced).

`flutter test --coverage` is what CI runs. One golden harness is skipped by
design (`dart_test.yaml`): its output embeds the date, so it is for looking
at, not asserting — `flutter test --tags golden --update-goldens
--run-skipped`, then open `test/golden/*.png`.

## 4. Supabase credentials (optional accounts)

`SupabaseConfig` reads `SUPABASE_URL` and `SUPABASE_ANON_KEY` via
`String.fromEnvironment`, which resolves at **compile time** (ADR-8). Omit
them and the app still runs — storage is local — but auth is swapped for
`DisabledAuthService` and Settings shows "Accounts unavailable". Hot reload
cannot fix that; only a rebuild can.

```bash
cp supabase.example.json supabase.json   # gitignored; paste your real values
scripts/build_android.sh run             # or apk / bundle / install
```

`scripts/build_android.sh` and every `.vscode/launch.json` configuration pass
`--dart-define-from-file=supabase.json` so the flag cannot be forgotten. **Never
run a bare `flutter build apk` for something you will hand to anyone** — it
silently ships with accounts off.

### One-time Supabase project setup

1. In the SQL editor, run `docs/cloud_backup_setup.sql`. It creates the
   `backups` table with row-level security and the `delete_my_account()`
   security-definer function that Settings → Account → Delete account calls.
   Without it, cloud backup and account deletion fail at runtime.
2. Authentication → URL Configuration: add
   `com.soshe90.ironyx://login-callback` to **Redirect URLs**, and move the
   Site URL off `http://localhost:3000`. Until then confirmation and
   password-reset links fall back to the Site URL and the deep link does
   nothing.
3. Before a public launch: confirm email confirmation and rate limits are on
   server-side, configure custom SMTP (the built-in sender is rate-limited),
   and check the free tier's pause-on-inactivity behaviour. See `TODO.md`,
   Week 2.

## 5. Release signing (Android)

`android/app/build.gradle.kts` signs `release` with a real key **only if
`android/key.properties` exists**; otherwise it silently falls back to the
debug key. A debug-signed bundle is not uploadable to Play. Both files below
are gitignored and are **not backed up by the repository** — losing the
upload key means never updating the listing.

```bash
keytool -genkey -v -keystore android/upload-keystore.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias ironyx_upload
```

`android/key.properties`:

```properties
storeFile=upload-keystore.jks
storePassword=...
keyAlias=ironyx_upload
keyPassword=...
```

Back both files up to two durable places the moment they exist. As of
2026-09-20 neither is present on the Windows development machine, and the
original key is confirmed lost — this is the recipe for its replacement
(safe because nothing was ever uploaded to Play under the old key; see
`TODO.md`, Week 0). After building, confirm the bundle is release-signed:

```bash
keytool -printcert -jarfile build/app/outputs/bundle/release/app-release.aab
```

The certificate owner and fingerprint must be your new key, not
"Android Debug".

Build and check a release:

```bash
scripts/build_android.sh bundle     # release AAB (shrunk + obfuscated)
```

- Release builds use R8 shrinking and `--obfuscate
  --split-debug-info=build/symbols/<version>`. `build/symbols/` is under the
  gitignored `build/`: **copy each uploaded build's symbols somewhere
  durable**, or that build's crash reports can never be symbolicated.
- Shrinking can break a plugin in ways only the release variant shows
  (`android/app/proguard-rules.pro`, `res/raw/keep.xml`). Run the release
  build on a real device before every store upload.
- Bump `version:` in `pubspec.yaml` (`1.0.0+N`); `kAppVersion` must match.

## 6. Windows notes

- Building or running with plugins needs **Developer Mode** (Settings →
  For developers) for symlink support. `analyze` and `test` do not.
- If the pub cache (`C:`) and the repo (`F:`) are on different drives, Kotlin
  incremental compilation breaks. Build with `-P kotlin.incremental=false`,
  or move `PUB_CACHE` onto the same drive as the repo.
- A release APK takes roughly 2.5–5 minutes to build.
